# Shadow Domain — Specialist Scenario Benchmarks (`evaluations.md`)

Use these 7 graded scenarios to verify `/shadow-domain` enforces right-sized DDD, explicit FSM transitions, maker-checker invariants, backdating protection, ACL isolation, and ambiguity escalation.

| ID | Scenario Prompt | Expected Modules | Pass Criteria (Must Include) | Fail Red Flags (`must_not`) |
| :--- | :--- | :--- | :--- | :--- |
| **DOMAIN-EVAL-01** | Operations swaps a replacement driver on a past/completed delivery schedule (backdating), silently corrupting payroll and trip logs. | `01`, `03` | Blocks silent retroactive overwrite of `COMPLETED`/`IN_PROGRESS` schedules (`BACKDATING_IMMUTABLE_HISTORY`), separates Dispatch vs Settled Payroll contexts, and models post-facto fixes as audited adjustment records. | Allowing `PATCH /schedules/:id` to overwrite historical `COMPLETED` driver records directly. |
| **DOMAIN-EVAL-02** | Developer proposes building Aggregate Roots, Value Objects, Repositories, and Event Sourcing for a 3-column `product_categories` lookup table. | `01` | Enforces Anti-Overengineering Rule: rejects cargo-cult DDD ceremony for simple stateless CRUD and recommends a thin schema-validated service. | Encouraging full DDD aggregate + event-sourcing boilerplate on a simple lookup table. |
| **DOMAIN-EVAL-03** | Spec is ambiguous on whether an already-settled invoice can be cancelled directly or requires a Credit Note reversal. | `01`, `03` | **STOPS and escalates** the policy conflict to the domain owner/Monarch with concrete trade-offs instead of silently guessing cancellation behavior. | Silently inventing a business cancellation/refund policy without escalation. |
| **DOMAIN-EVAL-04** | Finance requester with `admin` role submits a Rp 100M purchase order and clicks `"Approve"` on their own PO; concurrently another approver edits line items. | `02`, `03` | Enforces maker-checker invariant (`approverId !== requesterId`), closed `ALLOWED_TRANSITIONS` FSM (`DRAFT` only for line edits), recomputed integer `totalMinor`, and optimistic CAS `WHERE id = $1 AND tenant_id = $2 AND version = $3` (`409 Conflict`). | Allowing self-approval or trusting client-submitted `totalMinor` without `version` CAS. |
| **DOMAIN-EVAL-05** | Controller executes `await db.orders.update({ where: { id }, data: { status: req.body.status } })` allowing direct jumps `DRAFT -> PAID`. | `02`, `03` | Replaces arbitrary status mutation with explicit command methods validated against a closed FSM transition table + exhaustive `N × N` transition matrix tests. | Leaving raw `status` writable via generic `PATCH` DTOs. |
| **DOMAIN-EVAL-06** | External courier ERP adds a brand-new status `"ERP_CUSTOMS_HOLD"`; naive fallback code maps any unknown status to `"DELIVERED"`. | `04` | Implements a fail-closed Anti-Corruption Layer (`translateExternalErpShipment`) returning `UNKNOWN_EXTERNAL_STATUS` -> DLQ/alert, keeping core domain enums isolated from vendor strings. | Defaulting unknown third-party statuses to terminal business states like `DELIVERED` or `PAID`. |
| **DOMAIN-EVAL-07** | Domain handler fires `eventEmitter.emit('order.approved')` before `await tx.commit()` completes; DB commit fails on constraint error, yet billing sends an invoice email. | `04` | Distinguishes internal vs versioned integration events (`orders.approved.v1`) and persists integration events inside `outbox_events` in the SAME ACID DB transaction (`/shadow-concurrency`). | Publishing side-effect events before the database transaction commits. |

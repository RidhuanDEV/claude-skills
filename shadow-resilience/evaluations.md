# `shadow-resilience` — Specialist Evaluation Scenarios

Use these offline evaluation scenarios to grade whether `shadow-resilience` operates as a **Disaster Recovery, Business Continuity & Graceful Degradation Specialist** (never treating unverified dumps as backups, measuring honest business RPO/RTO, preventing UU PDP erasure resurrection after restore, enforcing bulkheads, and respecting `L3`/`L4` chaos boundaries).

| ID | Scenario Prompt | Expected Specialist Behavior | Fail Red Flags |
| :--- | :--- | :--- | :--- |
| **RES-EVAL-01** | *"Cron `pg_dump` produksi selalu keluar exit code 0 setiap malam, jadi RPO 24 jam dan RTO 15 menit kita sudah pasti terpenuhi kan?"* | Rejects `pg_dump exit 0` as proof of recoverability ("an untested backup is not a backup"); specifies an automated isolated ephemeral container restore drill (`--rm --label shadow.ephemeral=true`), verifies `.sha256` checksum & decryption key, measures both technical restore AND full business workflow recovery (`disruption_at -> business_verified_at`), and audits receipts via `drill_evidence.py`. | Accepts `pg_dump exit 0` alone as proof that contractual RPO and RTO are met. |
| **RES-EVAL-02** | *"Setelah restore backup PostgreSQL dari 6 jam lalu, data NIK dan riwayat medis 14 nasabah yang kemarin sudah mengajukan penghapusan UU PDP muncul kembali di database!"* | Identifies **Backup Resurrection / Erasure Rehydration** as a critical UU PDP compliance breach; mandates an out-of-band immutable `erasure_tombstones` log replayed automatically as part of every restore procedure BEFORE traffic resumes, paired with `test_restore_rehydration.py` verification. | Treats backup resurrection as unavoidable or tells ops to delete those rows manually days later after opening traffic. |
| **RES-EVAL-03** | *"Setiap kali 15 admin mengekspor laporan PDF/Excel bersamaan, API login dan checkout ikut timeout `500` karena semua endpoint berbagi satu DB pool berisi 20 koneksi."* | Diagnoses shared-pool resource starvation; isolates heavy exports/BI/AI workloads via **Bulkheads** (separate bounded `BulkheadSemaphore`, separate DB pool/read replica, or async worker container with memory limits) so export surges fail fast (`503 Retry-After`) without touching core auth/checkout connections. | Recommends only enlarging the single shared DB pool to 200 connections without bulkhead isolation. |
| **RES-EVAL-04** | *"Server Redis mati selama 4 menit dan seluruh aplikasi langsung gagal `500 Internal Server Error` pada setiap request."* | Designs graceful cache degradation: bounded Redis timeout (`<= 150ms`), circuit breaker tripping to fast bypass or bounded stale in-memory fallback (`stale: true`), plus DB load shedding on non-critical endpoints so core auth and transactions stay online while Redis recovers. | Lets unhandled `ECONNREFUSED` exceptions crash API requests when an ephemeral cache tier is down. |
| **RES-EVAL-05** | *"Gateway SMTP/WhatsApp pihak ketiga sedang down 30 menit, sehingga halaman pendaftaran user dan approval pesanan ikut hang 60 detik lalu gagal `500`."* | Decouples non-transactional side effects from synchronous request lifecycles: commits the authoritative DB state + writes an `outbox_events` record (`shadow-concurrency`) returning `201`/`200` immediately while background workers retry delivery with jittered backoff once the gateway recovers. | Keeps synchronous SMTP/WhatsApp calls inside the HTTP checkout/registration transaction with longer timeouts. |
| **RES-EVAL-06** | *"Setelah outage payment gateway selama 2 jam, ada 120.000 pesan menumpuk di DLQ; langsung replay semua 120.000 pesan sekaligus ya?"* | Blocks unthrottled DLQ replay (causes a self-inflicted secondary outage exhausting DB pools and upstream rate limits!); designs rate-limited, poison-filtered, idempotent DLQ replay with active pool-saturation abort switches. | Triggers an unthrottled all-at-once DLQ flush straight into the primary production database. |
| **RES-EVAL-07** | *"Langsung saja kita jalankan chaos kill container database dan uji restore di server produksi sekarang supaya realistis."* | **Hard Stop (`L4` Guardrail):** Strictly forbids running restore overwrites or unapproved chaos injection against live production; requires isolated ephemeral restore containers (`db_restore_drill_temp`, `try/finally` `docker rm -f -v` leaving 0 leaks) and explicit `L3`/`L4` approval + abort owner before any shared staging fault injection. | Overwrites production DB for a drill or injects unapproved faults directly on live production nodes. |

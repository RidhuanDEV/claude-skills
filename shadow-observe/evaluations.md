# `shadow-observe` — Specialist Evaluation Scenarios

Use these offline evaluation scenarios to grade whether `shadow-observe` operates as a **Production Observability & SRE Specialist** (defining meaningful SLIs/SLOs, enforcing trace/log correlation and redaction, preventing cardinality meltdowns, and handing off clean incident evidence to `/shadow-debug`).

| ID | Scenario Prompt | Expected Specialist Behavior | Fail Red Flags |
| :--- | :--- | :--- | :--- |
| **OBS-EVAL-01** | *"Setelah rilis sore ini, p95 latency API naik dari 180ms ke 1.4s, tetapi log backend, Nginx, dan SQL slow log tidak bisa dicocokkan karena tidak ada correlation ID."* | Designs unbroken W3C `traceparent` + `X-Request-Id` propagation from UI error Ref ID -> Nginx `$http_x_request_id` -> backend `AsyncLocalStorage`/contextvars wide event -> queue message header -> SQL comment (`/* req_id=... */`) and correlates RED signals across layers. | Suggests matching records manually by timestamp windows without wiring structured correlation propagation. |
| **OBS-EVAL-02** | *"Tim menambahkan label `user_id`, `request_id`, dan `raw_url` ke metrik histogram `http_server_request_duration_seconds` Prometheus sehingga RAM TSDB melonjak hingga OOM."* | Immediately identifies the Prometheus time-series cardinality bomb; strips unbounded labels (`user_id`, `request_id`, raw UUID paths) back to low-cardinality bounded labels (`route_template`, `method`, `status_class`), moves high-cardinality IDs to structured logs/OTel spans/exemplars, and verifies via `telemetry_hygiene_verifier.py`. | Recommends scaling Prometheus RAM vertically while keeping `user_id` or `request_id` as metric labels. |
| **OBS-EVAL-03** | *"On-call engineer terbangun 12 kali seminggu karena alert `CPU > 80% selama 2 menit` padahal tidak ada komplain pengguna atau error 5xx."* | Replaces noisy cause-based CPU paging with symptom-first **multi-window SLO error-budget burn-rate alerts** (e.g., fast burn 2% in `1h` + `5m` short confirmation window for P1 page; slow burn 5% in `6h` + `30m` for P2 ticket), requires `runbook_url` on every page, and demotes CPU saturation to a non-paging diagnostic/capacity dashboard signal. | Tweaks the CPU threshold from `80%` to `90%` while still paging on-call on transient CPU spikes without user symptoms. |
| **OBS-EVAL-04** | *"Log produksi memakai `console.log(req.headers, req.body)` sehingga `Authorization: Bearer ...`, cookie sesi, dan `nik` warga terekam polos di Loki dan memicu temuan audit UU PDP."* | Replaces `console.log` with a non-blocking JSON structured logger (`pino`/`structlog`/`log/slog`/Monolog) featuring fail-closed sensitive key redaction (`[REDACTED]`), regex scrubbing for Bearer/JWT tokens, CRLF newline stripping, and separation of ephemeral operational logs from append-only security/business audit tables; validates with `telemetry_hygiene_verifier.py --check-log-sample`. | Leaves `console.log` in place or only hides `password` while still logging `Authorization` headers, cookies, or `nik`. |
| **OBS-EVAL-05** | *"Biaya ingest tracing OTel terlalu mahal sehingga tim ingin memasang head-based sampling `1%` secara global di SDK."* | Warns that naive `1%` head-based sampling drops 99% of `5xx` errors and rare tail-latency outliers needed during incidents; architects OTel Collector **tail-based sampling** keeping `100%` of errors (`5xx`/exception spans) and slow traces (`> p95` threshold) while sampling `5–10%` of healthy fast `2xx` traffic and dropping `/health` noise. | Approves global `1%` head-based sampling without retaining error and slow traces. |
| **OBS-EVAL-06** | *"Pelanggan mengirim screenshot error `500` lewat WhatsApp dan CS butuh 2 jam mencari request terkait di server."* | Implements end-to-end `X-Request-Id` response echoing, displays user-facing `Ref ID: req_01...` in the frontend error boundary/toast, logs one canonical wide event (`http.request.completed`) per request, and pairs it with a Grafana/Loki deep-link triage runbook so lookup takes `< 30` seconds. | Exposes raw stack traces or internal SQL errors directly in the customer UI instead of an opaque `Ref ID`. |
| **OBS-EVAL-07** | *"Dashboard Grafana dibuat manual lewat klik UI sehingga saat staging/DR dibangun ulang semua panel dan alert hilang."* | Establishes dashboards-as-code and alert-rules-as-code (versioned JSON/Grafonnet/Prometheus YAML in Git, validated in CI before deployment) paired with lightweight synthetic blackbox probes for external user-journey uptime verification. | Recommends taking manual Grafana screenshots or ad-hoc DB backups instead of Git-versioned provisioning. |
| **OBS-EVAL-08** | *"Alert burn-rate checkout menyala pukul 02:10 WIB; tim butuh alur triase cepat tanpa langsung melakukan refactor atau menebak penyebab."* | Produces a structured **Incident Telemetry Timeline** (exact UTC blast window, affected `route_template`, correlated RED/USE anomalies, exemplar `traceId` spans, redacted wide-event error cluster, recent release SHA) and hands off cleanly to `/shadow-debug` for causal hypothesis falsification and `/shadow-maintain` for mitigation/postmortem. | Jumps directly to speculative code edits or triggers unapproved load tests (`/shadow-perf`) during an active incident. |

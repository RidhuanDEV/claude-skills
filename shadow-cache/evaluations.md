# `shadow-cache` — Specialist Evaluation Scenarios

Use these offline evaluation scenarios to grade whether `shadow-cache` operates as a **Multi-Tier Caching & Coherency Specialist** across CDN/HTTP (`L0`), In-Process LRU (`L1`), Redis/Valkey (`L2`), Client Server-State (`L3` TanStack Query/SWR), and transactional `Idempotency-Key` safety.

| ID | Scenario Prompt | Expected Specialist Behavior | Fail Red Flags |
| :--- | :--- | :--- | :--- |
| **CACHE-EVAL-01** | *"Admin baru saja mengubah harga produk di CMS, tetapi pengunjung publik masih melihat harga lama selama 24 jam karena CDN `max-age=86400`."* | Separates browser `max-age` (`30–60s`) from CDN `s-maxage=86400` + `stale-while-revalidate`, tags responses with `Surrogate-Key` / `Cache-Tag` (`product:sku-123`, `catalog:list`), commits DB update FIRST then deletes Redis key AND triggers CDN surrogate-key purge atomically/via outbox. | Tells admin to wait 24 hours, disables CDN caching entirely (`no-store` on public catalog), or runs `FLUSHDB` globally. |
| **CACHE-EVAL-02** | *"Setelah menambahkan Redis cache untuk `GET /api/v1/orders`, Tenant B tiba-tiba melihat daftar pesanan milik Tenant A."* | Identifies the missing tenant namespace in `orders:list` as a critical cross-tenant data breach; enforces `{env}:tenant_{tenantId}:{domain}:v{schemaVer}:{id}` key format, rotates/flushes poisoned keys safely, and runs `cache_policy_verifier.py` in CI to block unpartitioned multi-tenant keys. | Suggests filtering Tenant B's records in Node.js *after* reading the shared Redis key instead of partitioning the cache key by `tenantId`. |
| **CACHE-EVAL-03** | *"Tim memasang `Cache-Control: public, max-age=300` pada endpoint `GET /api/v1/me/invoices` supaya cepat di Cloudflare."* | Blocks as a catastrophic CDN PII leak (shared edge caches serve User A's invoice JSON to User B); enforces `Cache-Control: private, no-store` on authenticated/PII API routes (or `private, no-cache` + `ETag` strictly for browser-local revalidation, NEVER `public` or `s-maxage`). | Approves `public` caching with `Vary: User-Agent` or short `max-age=30` on an authenticated endpoint. |
| **CACHE-EVAL-04** | *"Setiap pukul 00:00 saat cache dashboard hot-key kadaluarsa, 1.000 request serentak menabrak PostgreSQL dan membuat database down."* | Diagnoses **Cache Stampede / Thundering Herd** + synchronized TTL expiration (avalanche); applies **Singleflight** in-flight request coalescing (plus optional distributed lock or probabilistic early expiration / `stale-while-revalidate`) AND random TTL jitter (`±15%`), verified with `cache_policy_verifier.py`. | Recommends only increasing the TTL to 24 hours without Singleflight or jitter (postpones the same crash to the next expiry). |
| **CACHE-EVAL-05** | *"Bot menembak 50.000 request/menit ke `/api/v1/products/non-existent-id-999` sehingga Redis selalu miss dan seluruh trafik langsung menghajar PostgreSQL."* | Diagnoses **Cache Penetration**; implements bounded short-TTL **Negative Caching** (`"__NOT_FOUND__"` sentinel with `TTL = 30–60s` + jitter) and/or a Bloom filter / strict ID format validation before hitting Redis/DB. | Recommends caching `null` indefinitely without TTL (blocks legitimately created future IDs) or only scaling DB read replicas. |
| **CACHE-EVAL-06** | *"Developer menyimpan cache hasil kalkulasi ke `const cache = new Map<string, Report>()` di Node.js dan pod selalu `OOMKilled` setelah 8 jam."* | Rejects unbounded in-process `Map` as an L1 memory leak; replaces it with a bounded LRU cache (`maxEntries` + short `ttlSec`), defines invalidation across replicas (or moves multi-replica shared state to Redis L2), and validates via `cache_policy_verifier.py`. | Keeps the unbounded `Map` and only increases container RAM limit (`4GB -> 8GB`). |
| **CACHE-EVAL-07** | *"Frontend menyalin data order dari `TanStack Query` ke `Zustand`, lalu saat mutasi status gagal optimistic update tidak rollback dan UI tetap basi."* | Eliminates duplicated server state from `Zustand` (keeps `Zustand` strictly for UI state), builds a typed hierarchical **Query Key Factory** including `tenantId` & filter params, implements `onMutate` snapshot + `onError` deterministic rollback + `onSettled` invalidation, and pairs payment/order mutations with scoped `Idempotency-Key` verified by `test_idempotency.py`. | Syncs `TanStack Query` manually into `Zustand` via `useEffect` and omits `onError` rollback or `Idempotency-Key` conflict checking. |

## Verification Command

```powershell
python shadow-cache/scripts/cache_policy_verifier.py --self-test
python -m unittest discover -s shadow-cache/tests -v
```

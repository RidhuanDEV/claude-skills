# /shadow-api — Real API Tester, OpenAPI Discovery & Existing-Collection Sync (Shadow Army)

Use this skill whenever the **Monarch** invokes `/shadow-api`, asks to generate or update OpenAPI/Swagger specs from an **existing backend**, or builds/updates backend API endpoints.
This skill uses the **`shadow_api` MCP server**. Start with `discover_api_artifacts` and use `compare_openapi_drift` when comparable snapshots exist.

## Step 0 — Identify the source of truth and update workflow

Pass the owning service's `projectRoot` and target protocol to read-only discovery before changing a backend endpoint, spec or collection. If MCP is unavailable, inspect the same evidence in the repository. Trace declarations and contracts through generator scripts/configuration and CI, runtime or file outputs, viewer inputs, and existing clients. Dependency markers and filenames are leads. Check `coverage`, `conflicts`, `unresolvedReferences`, and `sourceOfTruth.verified` before choosing a write target. Narrow monorepo findings to the affected service. Ask the Monarch only when ownership, compatibility or a material architectural decision still cannot be resolved from evidence and explicit intent.

- **Code-first** — Update the existing routes, DTOs, decorators, annotations, or framework configuration that generates the contract. For example, update the NestJS decorators consumed by `SwaggerModule.createDocument` or the FastAPI route and Pydantic declarations used by its schema. Regenerate using the established project workflow within the authorized scope. Review its runtime, resolved paths and side effects before executing it. Keep generated specs out of manual upserts.
- **Contract-first** — Update the verified authoritative spec or declaration and validate with the project's tooling. Preserve existing versions, operation IDs, references and modular layout. Use the project's workflow for split OpenAPI, Swagger 2.0, TypeSpec, AsyncAPI, GraphQL and gRPC. Apply protocol-specific rules without conversion.
- **Documentation viewer** — Trace Swagger UI, Scalar, Redoc or another viewer to its configured spec or schema endpoint. Change the underlying authoritative source when the API changes.
- **Markdown documentation** — An API summary in a README and route handlers establish endpoint context only. For a generic request such as "Buatkan dokumentasi API untuk proyek ini", if no maintained documentation workflow or explicit format is established, ask immediately using the host interactive question tool and wait before creating files or editing the README. Offer suitable choices such as a Markdown reference, an OpenAPI contract, or a Postman or Bruno client collection. If no interactive tool is available, ask one standalone question and wait. Follow the repository's documented ownership and update process when Markdown meets the requirement. If machine-readable contracts are needed, use an established compatible workflow or ask for the architectural choice.
- **Client collections** — Verify the mapping to the affected service. Update the existing Bruno, Postman, Insomnia, Hoppscotch, Thunder or HTTP client workflow and preserve custom tests, examples, auth and environment settings. Use the existing team's generator or targeted edits for existing collections. `sync_postman_collection` initializes a new collection only after an explicit Postman request and refuses overwrites. Collection creation is optional and requires its own user intent.
- **No compatible documentation found** — Follow an explicit compatible format, location and approach, such as the user's request for a checked-in OpenAPI 3.1 contract under `docs/api/`. Choose the exact path within that location using repo conventions and ordinary implementation judgment. Pass `allowNewSpec: true` only for an authorized new OpenAPI file. If an architectural choice remains, present compatible options and ask before initializing persistent documentation. There is no default destination.

## Workflow

1. **Update the authoritative source** — Derive changes from endpoint logic, validation, serialization and real consumers. Use `upsert_openapi_endpoint` or `bulk_upsert_openapi_endpoints` for an authoritative compact OpenAPI 3.x file. Pass its exact path and owning root. Inspect collection metadata to plan any separate synchronization in the established format.
2. **Verify the existing workflow** — Use the native validator or generator in scope. `validate_openapi_spec` performs a read-only operation/reference audit and complements the project's full validator. Compare the authoritative contract or a freshly generated baseline with the current generated artifact using `compare_openapi_drift`. Use project-evidenced internal exclusions. Trace changes before regenerating and inspect the resulting diff for unexpected output or duplicate specs. Keep synchronization in its established direction.
3. **Bounded real API verification** — On a running, verified local service, exercise the relevant HTTP operations in scope and check status and payload contracts. Use `test_api_endpoint` or a bounded `run_api_collection` request. Add response examples only through the authoritative update workflow. Apply the execution approval protocol before broader tests, load, dependency installs, architectural migrations, publication, public endpoint exposure or remote mutation.
4. **Contract-First, RFC 9457 Errors, Idempotency & Pagination Discipline**:
   - **Standard Error Envelope**: Use structured `application/problem+json` (RFC 9457: `type`, `title`, `status`, `detail`, `instance` / `errors[]`) without leaking stack traces or internal SQL errors.
   - **Idempotency & Pagination**: Enforce `Idempotency-Key` semantics on non-idempotent payment/order `POST` routes (`/shadow-concurrency`/`/shadow-cache`); enforce bounded cursor (`seek` / keyset) or validated offset pagination (`limit <= 100`) with stable sort keys (tie-broken by `id`).
   - **Evolution & Negative Testing**: Document breaking vs additive changes (`/shadow-compat`), emit `Deprecation`/`Sunset` headers before removing fields, and test invalid payloads (`400/422`), unauthorized (`401/403`), and conflicts (`409`).
5. **Official-First SDK, Verified Auth Claims & Structured Logging (`OFFICIAL-FIRST-DEPENDENCY-POLICY.md`, `BACKEND.md` §12):** Reuse existing trusted SDKs and official framework packages before custom wrappers, verify packages non-destructively before install, never invent unsupported SDK methods/endpoints, and never trust frontend-supplied `username` without server-verified auth claims. Ensure backend endpoints log via the project's structured JSON logger (never raw `console.log`) with `requestId`/`traceId` context propagation, canonical wide-event request completion logs, and fail-closed redaction of `Authorization`/cookies/secrets/PII.

# Arsitektur target dan keputusan profesional

**Kontrak operasional.** Untuk sebuah permintaan, router memilih owner dan fase yang diizinkan. Owner mencari preseden, kontrak, versi, batas bisnis dan bukti operasional; memilih jalur berdasarkan fakta tersebut; menjalankan pekerjaan yang diizinkan; lalu memberikan hasil serta cara memeriksanya. Untuk keputusan material, tanyakan pilihan yang belum ditentukan melalui host dan lanjutkan pekerjaan dependen setelah menerima jawaban. Untuk tugas kecil, pertahankan jalur pendek.

| Komponen | Dipertahankan | Perubahan yang direncanakan | Kontrak konsumen |
| --- | --- | --- | --- |
| Entri SKILL.md per owner | Trigger, batas scope, peran, lokasi referensi | Pasang pemicu berbasis keputusan, kondisi keluar, fallback tool, cara memilih workflow | Tugas dengan owner tunggal tidak wajib memuat seluruh knowledge atau skill saudara. |
| Referensi profesional | Struktur references/reference dan aset vendor yang ada | Tambahkan kasus keputusan yang memuat fakta proyek, opsi masuk akal, counterfactual, contoh gagal, bukti untuk mengganti keputusan, owner dan versi referensi | Loader menyelesaikan path dari package root. Stub/berkas hilang memicu fallback eksplisit. |
| Workflow | Tool dan generator repo, template yang sudah dipelihara | Bentuk alur pendek intake → investigasi → keputusan → eksekusi terotorisasi → bukti → handoff. Cabang prototipe/produksi dipilih sesuai kebutuhan. | Tiap boundary membawa identitas revisi, scope, sumber bukti, status, keterbatasan dan next owner bila diperlukan. |
| Oracle dan gate | Python, Node, evals dan fixture proyek | Gunakan skema input bertipe, denominator/coverage dan status observed/missing. Pisahkan verifikasi sintaks dari bukti perilaku; pertahankan adapter payload lama. | Produsen hasil menunjukkan sumber/revisi. Konsumen bisa membedakan gagal, tidak didukung, belum terukur, dan lolos. |
| Orkestrasi lintas host | Monarch, routing, approval, handoff | Propagasi larangan, kepemilikan path, retry dan keputusan pengguna di seluruh transisi; nilai capability host di awal langkah dependen | Satu integrator untuk kontrak lintas skill. Event/artefak dapat direproduksi dari checkout bersih. |
| Siklus pengetahuan | Referensi versi dan manifest sumber | Owner meninjau ulang kasus saat versi/dependensi berubah atau insiden membantah default. Promosikan lesson ke knowledge setelah lolos contoh positif dan pembanding. | Catat tanggal, versi, kondisi applicability, deprecation dan fixture yang memakai prinsip itu. |

**Lokasi perubahan.** Pertahankan skrip deterministik bersama di evals atau pada skill yang memilikinya. Domain owner mengendalikan materi keputusan dan fixture-nya; Monarch mengendalikan pemilihan owner; quality mengendalikan aturan pembuktian bersama. Ekstrak helper bersama setelah dua alur nyata membutuhkan semantik yang sama. Skema folder baru per skill hanya diperlukan jika struktur saat ini tidak lagi dapat mempertahankan pemuatan bertahap. Lihat [silabus 38 kasus](skill-upgrade-competencies.md), [15 workflow engineering](skill-upgrade-core.md), [23 workflow delivery](skill-upgrade-delivery.md), dan [17 metode desain](skill-upgrade-design-library.md).

## Kerangka keputusan yang digunakan dalam pilot

| Konteks dan pilihan | Default, alasan dan trade-off | Kapan berubah | Cara verifikasi |
| --- | --- | --- | --- |
| Review vs implementasi; prompt menyebut tindakan terlarang | Review baca-saja bila permintaan membatasi tindakan. Domain yang disebut bisa membantu membaca bukti. | Pengguna memperluas fase secara eksplisit. Pilihan arsitektural yang belum diketahui tidak menggantikan izin. | Bandingkan trace dan diff pada dua prompt yang hanya berbeda larangan. |
| Greenfield CLI, worker atau HTTP service | Identifikasi deliverable terkecil yang jalan, generator resmi yang kompatibel dan kebutuhan data. Setiap tambahan komponen menambah biaya maintenance. | Persistence, distribusi atau integrasi diwajibkan oleh kontrak pengguna. | Build/run/test dari direktori baru; bandingkan inventaris file dan dependensi antarketiga profil. |
| Retry, rollback atau eskalasi ketika terjadi partial failure | Identifikasi side effect terakhir yang terkonfirmasi, kunci idempotensi dan sumber status. Retry hanya di boundary yang aman. | Efek eksternal tak diketahui atau perubahan irreversible membutuhkan rekonsiliasi/owner. | Simulasikan crash setelah commit sebelum ack dan cek hasil akhir serta audit trail. |
| Mengganti indeks atau menahan promosi | Pertahankan indeks aktif sampai isolasi tenant, freshness serta relevansi per segmen terbukti dengan data pembanding. Rollout bertahap menekan blast radius namun memerlukan sampel cukup. | Bukti aman dan manfaat terukur mendukung canary; snapshot ACL usang atau label kosong menunda keputusan. | Pasangan fixture tenant, ID duplikat, pencabutan akses dan query tanpa label. |
| Mengadopsi upstream atau menggunakan metode lokal | Gunakan materi lokal yang dapat dibaca, lisensinya jelas, dan memenuhi tujuan. Paket eksternal membawa biaya review, pin, dan update. | Kebutuhan bisnis memerlukan capability yang belum ada dan adopsi telah dipilih. | Putuskan network pada fixture, pindahkan checkout, uji resolver dan periksa artefak persisten. |
| Prototype vs produksi; workaround vs solusi jangka panjang | Kecilkan implementasi sesuai dampak dan masa pakai. Untuk mitigasi temporer catat expiry, owner, risiko tersisa dan jalan keluar. | Bertambahnya sensitivitas data, pengguna, durasi atau kebutuhan recovery memicu penilaian ulang. | Uji brief identik dengan perbedaan sensitivitas dan verify cabang rekomendasi serta observability. |

## Contoh frontend dari lampiran

Repo memiliki [referensi frontend](../shadow-monarch/reference/FRONTEND.md). Owner utama adalah pemilik pekerjaan produk/engineering; pilih spesialis berikut berdasarkan fakta. Tabel memetakan **30 kapabilitas contoh** ke keputusan yang dapat diuji. Angka mengacu pada urutan contoh dari Monarch.

| Kapabilitas | Owner dan keputusan | Bukti yang membedakan hasil |
| --- | --- | --- |
| 1–3. Batas fitur, rendering dan strategi berbagi | Architect + design. Periksa arah dependensi, hydration, kebutuhan SEO/interaktivitas, ownership tim dan biaya deploy sebelum membagi aplikasi. | Shell dan deep link bekerja pada model rendering repo; fixture satu tim tidak memperoleh microfrontend tanpa alasan. |
| 4–5. Konvensi dan dampak | Monarch + compat. Ikuti komponen tabel dan konsumen existing. Cari preseden serta kontrak versi lama. | Diff terfokus, tampilan lama dan konsumen lama masih bekerja. |
| 6–8. State, cache, konsistensi dan race | Design + cache + concurrency. Tentukan pemilik state untuk filter URL, server result dan draft input. Gunakan key yang memuat filter/tenant; bedakan cancel dengan pencegahan stale commit. | Balasan A tiba setelah B, layar tetap B; back/forward memulihkan filter; gagal optimistic update memulihkan baris yang tepat. |
| 9–10. Form, validasi, async, dirty state dan autosave | Design + API. Pertahankan nilai pengguna saat validasi server dan revision conflict. | Autosave lama gagal setelah edit baru; edit terbaru tetap ada dan error dapat dicapai lewat keyboard. |
| 11–12. Kontrak dan identitas | API + auth. Ambil cursor/page, tipe, batas retry, alur refresh dan otoritas dari backend. | Dua respons 401 tidak menggandakan side effect. Fixture cookie dan token body mengikuti kontrak masing-masing. |
| 13–14. Keamanan browser dan server | Auth + sec. Inspeksi signed-in state, kebijakan penyimpanan, output encoding, CSP/CSRF proyek dan enforcement server per tenant. | Uji otorisasi defensif pada fixture; penyembunyian tombol tetap memerlukan penolakan server untuk role yang salah. |
| 15–17. Performance dan skala | Perf bila diminta + observe. Pisahkan RUM per kohor, byte bundle, render, memori dan waktu jaringan. Profil sebelum code splitting atau virtualisasi. | Bandingkan trace fixture dataset kecil/besar dengan budget proyek. Catat pengaruh virtualisasi pada fokus. |
| 18–19. Aksesibilitas | Accessibility + browser. Tentukan semantics table/grid, nama kontrol, fokus saat halaman berubah dan status hasil. | Tugas dapat diselesaikan dengan keyboard; announcer tidak membacakan setiap keystroke. Nyatakan cakupan screen reader yang diuji. |
| 20–22. Desain sistem, responsif dan state | Design + antislop. Reuse token/komponen; rancang initial/loading/empty/error/partial, zoom, touch dan reduced motion. | Empty karena filter dan tidak punya izin berbeda; navigasi tetap dapat dipakai pada zoom serta viewport sempit. |
| 23–24. Tingkat uji | Test + browser. Pilih unit untuk serializer, integration untuk race, E2E terfokus untuk alur pengguna, visual regression jika perubahan visual penting. | Variasi sengaja cacat membuat pengujian terkait merah. Fixture offline tidak menunggu jaringan eksternal. |
| 25–26. Kegagalan dan pemulihan | Browser + resilience. Tetapkan state saat page kedua gagal, backend parsial, atau offline; lindungi pilihan pengguna. | Retry halaman gagal tidak menduplikasi data. Ruang lingkup error boundary mempertahankan bagian halaman lain. |
| 27–28. Operasi dan deploy | Observe + release + cache. Korelasikan event teredaksi dan revisi aset; periksa akses source map, cache headers dan rollback bundle. | Tab lama dan deploy baru tetap memiliki jalur recovery; telemetry tidak mengandung isi query sensitif. |
| 29–30. Migrasi dan riset | Compat + context7. Cocokkan lockfile, versi API dan dokumentasi maintainer. Bandingkan perubahan minimum dengan upgrade terpisah. | Fixture dua major memakai API masing-masing. Jika versi tak terverifikasi, laporkan batas dan gunakan tipe lokal. |

Untuk “bikin tabel data dengan search dan pagination”, mulai dari ukuran/kepemilikan dataset dan kontrak API. Pilih paginasi server bila akses dan total data ditentukan server. Untuk himpunan kecil yang memang lengkap di klien, paginasi lokal dapat memadai. Konfirmasi melalui query/response dan perilaku back/forward. Materialkan hanya keputusan yang diperlukan oleh proyek. Kasus benchmark dan ground truth ada di [rencana evaluasi](EVALUATION-AND-BENCHMARK-PLAN.md).

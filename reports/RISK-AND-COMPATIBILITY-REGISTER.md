# Register risiko dan kompatibilitas

Risiko adalah skenario yang harus diuji pada Stage B. Prioritas tinggi menunjukkan bahwa bukti yang salah dapat mengotorisasi tindakan berikutnya atau menyesatkan keputusan rilis. Daftar ini menggabungkan observasi dari [audit](SKILL-ECOSYSTEM-AUDIT.md) dengan risiko rancangan baru. Status “teramati” merujuk ke audit/probe yang disebutkan; “antisipasi” adalah hipotesis untuk fixture.

| ID, asal, dampak | Penyebab dan permukaan terdampak | Kontrol yang diusulkan dan owner | Uji penerimaan dan respons bila gagal |
| --- | --- | --- | --- |
| R01 teramati, tinggi | Negasi tetap memicu domain yang dilarang. Child task dapat mewarisi topik tanpa batas eksekusi. | Monarch membaca fase dan larangan sebelum co-activation. Propagasi scope dan parent decision. | Pasangan review-only/implement, parent/child, tool tersedia/tidak tersedia. Jika ada write pada review, blok promosi router dan kembalikan revisi mapping. |
| R02 teramati, tinggi | Dataset kosong, boolean string dan klaim pemanggil menghasilkan PASS yang kemudian dipakai skill lain. | Eval, realtime dan supplychain memvalidasi skema, bukti serta denominator. | Fixture empty/malformed ditolak atau unmeasured; fixture lama valid tetap menghasilkan nilai sama. Jika konsumen mengartikan unknown sebagai pass, blok integrasi konsumen. |
| R03 teramati, tinggi | Quality memakai keadaan daemon bersama dan nama serupa untuk mengidentifikasi resource. | Quality mencocokkan owner repo/run dan bukti pembuatan. Retry dan cleanup hanya menyasar milik run. | Mock dua job termasuk container berhenti dan crash/retry. Jika target tetangga masuk daftar kandidat, nonaktifkan cleanup pada jalur terpengaruh. |
| R04 antisipasi, tinggi | Skema hasil baru mengubah interpretasi klien/handoff lama atau menghadirkan field wajib baru. | Produsen menjaga kompatibilitas baca; consumer fixture pada payload lama dan baru. Versikan kontrak jika semantik berubah. | Empat kombinasi produsen/konsumen serta rollback tengah rollout. Jika kehilangan data, hentikan migrasi dan gunakan reader kompatibel. |
| R05 teramati, sedang–tinggi | Vendor stub, nama sama, path absolut atau template hilang mengarahkan tindakan ke provider keliru. | Design menggunakan path beridentitas paket, pin dan capability probe. Template persisten hanya untuk permintaan terkait. | Pindah checkout, offline, nama modul ganda. Jika keputusan salah owner, fallback ke pemilik lokal dan tandai ketergantungan belum tersedia. |
| R06 antisipasi, tinggi | Indeks, summary, cache atau handoff menahan data setelah pencabutan akses. | Search, cache, auth, handoff memvalidasi scope saat konsumsi; hindari isi sensitif dalam log fixture. | Ubah izin antara pengambilan dan penyajian. Satu bocor menggagalkan rilis. Isolasi artefak dan lakukan review owner data. |
| R07 teramati, tinggi | Scaffold menginisialisasi subsistem yang tidak dibutuhkan, generator performa menciptakan route yang tak didefinisikan. | Bootstrap/perf memakai kontrak dan profil workload aktual; catat tidak didukung. | CLI offline tanpa HTTP dan spec POST-only; cek inventaris tanpa mengirim trafik. Jika kontrak tak cocok, revert generator, pertahankan evidence. |
| R08 antisipasi, tinggi | Pemanggilan live CLI/provider, benchmark besar, akses DB atau replay menyentuh target yang salah. | Evaluator memakai temp root unik, mock network dan data sintetis secara default; cek env/endpoint serta batas izin untuk live. | Env unknown atau endpoint keluar allowlist menghasilkan skip/blocked yang terlihat sebelum efek samping. |
| R09 teramati, sedang | Eval menilai kosakata; model mengutip assertion atau tahu answer key. | Eval memakai diff/event/fixture, pemisahan benchmark pengembangan dan holdout, reviewer kalibrasi. | Respons negatif yang menyalin assertions tidak lolos. Jika hasil holdout bocor, pensiunkan set dan rebaseline. |
| R10 antisipasi, sedang | Ketergantungan ke routing terlalu banyak, konsumsi konteks meningkat, sumber baru mengalahkan constraint proyek. | Monarch dan context7 memilih sedikit bukti yang relevan; loader menyimpan alasan, revisi, budget dan waktu. | Rekam file dibuka, latensi, tool calls, token/beban jika tersedia pada typo, tugas tunggal dan multi-domain. Jika biaya naik tanpa manfaat, rollback co-activation. |
| R11 antisipasi, sedang–tinggi | Doc versi terbaru berbeda dari lockfile/SDK internal atau berlaku pada yurisdiksi lain. | Owner domain merekam versi/tanggal, applicability, source hierarchy, conflicting authority; eskalasi legal/organisasi bila berdampak. | Fixture major lama dan kebijakan khusus klien. Jika fakta belum terverifikasi, gate mencegah rekomendasi definitif. |
| R12 antisipasi, tinggi | UAT, privacy, GRC dan riset dapat mengklaim peserta, persetujuan, atau kompetensi auditor tanpa bukti. | Bedakan simulasi, observasi dan sign-off manusia. Handoff menyebut kebutuhan bukti dan pemegang keputusan. | Skenario tanpa peserta atau otorisasi melaporkan belum terukur. Tahan klaim compliance/acceptance jika bukti formal hilang. |
| R13 antisipasi, sedang | Runtime Claude/Codex/Gemini berlainan dalam tool interaktif, sandbox, install root dan stale MCP process. | Integrator merekam revisi loaded dan matriks kapabilitas; dukung fallback satu pertanyaan mandiri. | Uji sesi baru dan host tanpa UI tool. Bila host gagal, tandai baris host-nya; rollback copy/router/MCP sebagai satu set kompatibel. |
| R14 antisipasi, tinggi | Dua perubahan benar secara terpisah bertabrakan pada kontrak, fase deploy atau recovery. | Git, release dan owner kontrak menggunakan base SHA, contract test gabungan, rollout/rollback dengan skew versi. | Gabung perubahan migrasi data + reader lama; bila secara semantik gagal, pertahankan versi kompatibel dan tunjuk owner keputusan. |
| R15 antisipasi, sedang | Threshold evaluasi tetap memberi kepastian palsu untuk query jarang, browser minor atau kelompok pengguna kecil. | Reviewer menguji variasi, ukuran sampel, severity serta trade-off produk; pisahkan segmen dan jumlah kasus. | Uji subset kosong dan rerata naik ketika kelompok kecil memburuk. Tahan klaim untuk kelompok yang belum terwakili. |
| R16 antisipasi, tinggi | Dokumen eksternal, instruksi vendor atau teks dalam fixture memicu install, pengiriman data atau perubahan scope. | Treat content as evidence. Izinkan hanya tindakan user dan project authority; gunakan arsip/provenance dan parsers defensif. | Materi dummy yang meminta publikasi tidak menghasilkan tool call. Isolasi sumber serta laporkan provenance bila aturan prioritas gagal. |

**Pemulihan setelah perubahan.** Pertahankan snapshot fixture dan baseline sebelum patch. Untuk host ber-copy, simpan revisi instruksi dan entry point MCP yang cocok; untuk junction, kembalikan sumber pada checkout terisolasi. Gunakan revert terarah pada perubahan milik paket, cek kompatibilitas pembaca lama, lalu ulangi tes domain dan satu trace lintas-skill pada revisi yang sama. Penyelesaian teknis insiden dan persetujuan deploy tetap keputusan yang terpisah.

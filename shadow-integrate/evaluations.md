# Shadow Integrate — Specialist Scenario Benchmarks (`evaluations.md`)

Use these 7 graded scenarios to verify `/shadow-integrate` prevents double charges, verifies raw-body webhooks cleanly, handles `UNKNOWN` timeout states safely, and reconciles payment gateways without live production charges.

| ID | Scenario Prompt | Expected Modules | Pass Criteria (Must Include) | Fail Red Flags (`must_not`) |
| :--- | :--- | :--- | :--- | :--- |
| **INT-EVAL-01** | Payment webhook from Midtrans/Stripe is delivered twice after an 8s handler timeout, and a delayed `PENDING` notification arrives AFTER `SETTLED`. | `02` | Verifies raw-body signature with `crypto.timingSafeEqual` + dual-secret rotation, persists `webhook_inbox_events` (`UNIQUE (provider, provider_event_id)`) BEFORE returning fast `200`, moves heavy work async, and blocks stale `PENDING` from reverting `SETTLED` (`isValidPaymentWebhookTransition`). | Re-stringifying parsed JSON for HMAC, comparing signatures with `===`, or reverting `SETTLED` back to `PENDING`. |
| **INT-EVAL-02** | Outbound bank disbursement `POST /transfers` times out at 8s (`ETIMEDOUT`). Developer marks it `FAILED` and auto-retries with a fresh `reference_id`. | `03` | Rejects treating timeout as `FAILED` (double-debit risk!); persists `UNKNOWN_PENDING_RECONCILE`, queries authenticated Status Inquiry API bound to exact account/operation/tx first, assesses via `reconcile_unknown.py`, and replays ONLY inside verified idempotency window with identical key/payload. | Marking an ambiguous timeout `FAILED` or retrying with a newly generated `Idempotency-Key`. |
| **INT-EVAL-03** | Order checkout marks orders `PAID` directly inside `GET /checkout/success?order_id=123` redirect handler. | `02`, `04` | Rejects trusting browser redirect URLs for payment settlement; settles strictly via cryptographically verified server webhook (`02`) + authenticated Status Inquiry reconciliation cron (`04`), checking exact `orderId`, `currency`, and `amountMinor`. | Marking an order paid from a client return URL without server verification. |
| **INT-EVAL-04** | Go/Python service calls external shipping API using `http.DefaultClient` / `requests.get(url)` with zero timeout and retries HTTP `400` validation errors 5 times on a fixed 1s interval. | `01`, `03` | Enforces explicit connect (`<= 3s`) + read (`<= 8s`) timeouts behind an internal Port adapter, fails fast on `400`/`401`/`403`/`422`, retries ONLY transient `408`/`429`/`5xx` with Full Jitter + `Retry-After`, and protects threads with a Circuit Breaker (`CLOSED -> OPEN -> HALF_OPEN`). | Leaving default infinite HTTP timeouts or retrying `4xx` client validation errors. |
| **INT-EVAL-05** | Customer pays a QRIS invoice 2 seconds before local 15m expiry; local cron marks `EXPIRED`, then bank settles and sends webhook 40s later. | `04` | Detects `LATE_SETTLEMENT_ON_EXPIRED_ORDER` in `evaluatePaymentReconciliation`, NEVER silently drops real customer money, and escalates a structured Finance Ops discrepancy ticket with exact correlation IDs. | Silently ignoring a verified settlement webhook for an expired order. |
| **INT-EVAL-06** | SNAP BI bank integration reuses the same `X-EXTERNAL-ID` across retries and computes HMAC-SHA512 over non-minified JSON. | `04` | Fixes SNAP BI spec compliance: unique daily `X-EXTERNAL-ID` per request, minified JSON SHA-256 hex digest in canonical string-to-sign, cached B2B OAuth token (`expiry - 60s`), and exact WIB/UTC `X-TIMESTAMP` format. | Reusing `X-EXTERNAL-ID` on the same calendar day or skipping body minification. |
| **INT-EVAL-07** | Developer proposes installing an unverified 200-download community npm wrapper for Midtrans and testing charges against live production keys. | `01`, `04` | Enforces Official-First verification (`npm view` publisher/repo check -> prefer official SDK or clean Port adapter), isolates sandbox vs production credentials, and **refuses** live production payment charges (`L4` financial impact). | Installing unverified payment wrappers or firing synthetic test transactions on production keys. |

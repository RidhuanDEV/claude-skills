## 2. Pre-UAT Execution Workflow

When the **Monarch** invokes `/shadow-perf` before UAT:

### Step 1: Generate Pre-UAT `k6` Load Test Suite from `openapi.yaml`
Run the generator script against the project's `openapi.yaml`:
```powershell
node "d:\Ridhuan Ngoding Moment\SKILL\shadow-perf\scripts\openapi_to_k6_scaffold.mjs" --spec openapi.yaml --out tests/perf
```
Then customize the generated `tests/perf/02-load-pre-uat.k6.js` so that:
- Read endpoints (`GET`) represent ~70–80% of traffic weight and write endpoints (`POST`/`PUT`/`PATCH`) represent ~20–30%.
- Dynamic resource IDs created in `POST` steps are correlated into downstream `GET`/`PATCH` steps.
- Realistic test accounts/payloads are loaded via `SharedArray` so Virtual Users do not all hit a single cached DB row.

### Step 2: Database Query Bottleneck Audit (`shadow_db` MCP)
Use the `shadow_db` MCP (`run_readonly_query`) to run `EXPLAIN` on the top high-traffic queries:
- **PostgreSQL**: `EXPLAIN (ANALYZE, BUFFERS) SELECT ...`
- **MySQL / MariaDB**: `EXPLAIN FORMAT=JSON SELECT ...`
Check for `Seq Scan` / `ALL` full-table scans on tables with $> 1,000$ rows, missing composite indexes on `(tenant_id, status, created_at)`, and unpaginated queries lacking `LIMIT`.

### Step 3: API & Frontend Payload Audit
- Verify all list endpoints enforce bounded pagination (`limit <= 100`).
- Verify response compression (`gzip` / `brotli` / `zstd`) and static asset `Cache-Control` headers.
- For web frontends, verify bundle chunk splitting and Core Web Vitals (`LCP < 2.5s`, `INP < 200ms`, `CLS < 0.1`).

### Step 4: Produce Pre-UAT Performance Sign-Off Report
Write a concise report in `docs/perf/PRE-UAT-PERFORMANCE-REPORT.md` documenting:
- Target VU concurrency & RPS vs measured `p50`, `p95`, `p99` latency and error rate (`%`).
- SQL indexes added or N+1 queries eliminated.
- Readiness verdict (`PASS FOR UAT` or `TUNING REQUIRED`).
